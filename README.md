# TV Overlay Refactor — решение

Рефакторинг TV-оверлея видеоплеера. Исходный текст задания — в [TASK.md](TASK.md).

> **Статус: работа в процессе.** Каркас по слоям и точка входа переработаны;
> состояние плеера, фокус и распил оверлея — впереди. Разделы ниже дополняются
> по мере работы.

---

## Запуск

```bash
flutter pub get
flutter run
```

Нужен эмулятор Android TV (профиль Television 1080p, образ Android TV arm64
на Apple Silicon) либо реальная приставка. На телефоне приложение сознательно
показывает заглушку: `UiModeManager` не сообщает о режиме телевизора.

### Две ловушки окружения, на которые стоит заложить время

**Ссылка в исходном коде мертва.** `ya-1.kuzalex.com` резолвится, но соединение
не устанавливается. Рабочий адрес был закомментирован строкой выше; сейчас
используется он.

**Видео не отрисовывается на эмуляторе «из коробки».** Это открытый баг
media_kit — [media-kit#1343](https://github.com/media-kit/media-kit/issues/1343).
На эмуляторе media_kit принудительно ставит `vo: gpu`, а libmpv не может создать
EGL-контекст на гостевом драйвере: в логе `eglCreateContext ... EGL_BAD_ATTRIBUTE`.
Звук при этом идёт, картинки нет. Обходится конфигурацией `vo: mediacodec_embed`
+ `hwdec: mediacodec` — она была в исходном коде задания и оказалась верной:
MediaCodec рисует прямо в Surface, EGL не участвует.

Одного обхода мало: в связке с `mediacodec_embed` эмуляторный декодер
`c2.goldfish.h264.decoder` виснет на **мастер-плейлисте** HLS (в логе
`Query output surface allocator returned 0 params => BAD_INDEX`, позиция стоит
на 00:00, звука тоже нет). Проверено на трёх сборках, отличавшихся только
ссылкой: мастер — зависание, одиночный вариант 320×184 — играет, одиночный
вариант 1280×720 — играет. Поэтому [sample_content.dart](lib/app/sample_content.dart)
указывает на один вариант.

Наконец, запуск воспроизведения на эмуляторе просто **нестабилен**: из четырёх
запусков одного и того же кода срабатывают примерно два. Увидели чёрный экран —
сначала перезапустите приложение.

На реальной приставке ничего из этого не воспроизводится: там работает ветка с
конфигурацией по умолчанию.

## Проблемы исходной реализации

### Ошибки

**Поиск фокуса по `debugLabel` не работает в release.** Кнопка play/pause
искалась как `node.debugLabel == 'action'`, но сеттер `FocusNode.debugLabel`
присваивает значение внутри `assert`. В release-сборке метка всегда `null`:
начальный фокус не устанавливается, проверка `hasFocus` в корневом обработчике
не проходит никогда.

**Висячий callback после `dispose`.** `_controller.onOverlayHided ??= _onOverlayHided`
отдавал контроллеру (живёт дольше виджета) ссылку на метод `State`, и в
`dispose` она не очищалась. Таймер скрытия мог дёрнуть `requestFocus()` на
уничтоженном узле.

**Throttle позиции ломался при перемотке назад.** Сравнивалось
`current - last >= 1s`; после seek назад разница отрицательная, поле не
обновлялось, и слушатель молчал, пока позиция не догонит старое значение. На
нём висел перевод фокуса на `Skip intro`.

**`!` на nullable-полях по всему оверлею.** Работало лишь потому, что оверлей
строился после инициализации — неявная зависимость от порядка.

### Архитектура

**Двойное управление состоянием.** `PlayerController` — это `ValueNotifier`, а
`PlayerBloc` поверх него чистый прокси: каждый тик позиции гонялся через очередь
событий блока впустую. Мутабельный контроллер при этом лежал внутри
`Equatable`-состояния и участвовал в `props` по ссылке.

**UI-логика в видеоконтроллере.** `showOverlay`, публичный `overlayTimer` и
`onOverlayHided` жили рядом с media_kit, а виджет лазил в их внутренности.

**Маршрутизация фокуса размазана по пяти обработчикам**, каждый сам решал, куда
прыгать по стрелкам, и дёргал `setState` всего оверлея ради подсветки одной
кнопки.

**Мёртвый и дублирующий код.** Ветка play/pause в корневом `FocusScope` была
недостижима (`FocusWrapper` перехватывал submit раньше); debounce клавиш в корне
не работал, потому что события идут от сфокусированного узла вверх; время
рисовалось дважды; `ScrollViewFocusScopeNode.enableAnimation` и
`FramePlayerProgressBar.color` не использовались.

**Требование README про частые обновления позиции нарушалось**: верхняя панель
перестраивалась на каждый тик, а остальные builder'ы «оптимизировались» хаками
с мутабельными полями внутри `buildWhen`.

## Структура решения

```
lib/
  main.dart            — точка входа
  app/                 — composition root: сборка зависимостей, сэмпл-контент
  domain/              — чистый Dart: ни Flutter, ни media_kit
  services/            — реализации: media_kit, платформенный канал
  presentation/        — экраны, блоки, виджеты
  core/                — общие утилиты и константы
```

Правило зависимостей: `domain` не знает ни о ком, `services` и `presentation`
зависят от него, а друг с другом встречаются только в `app/`.

Слоя usecase нет намеренно: в приложении с одним экраном он выродился бы в
проброс `PlayUseCase → repository.play()`.

### Принятые решения

**`DeviceInfo` провайдится значением, а не репозиторием.** Информация об
устройстве загружается один раз, нужна до выбора экрана и дальше неизменна.
Репозиторий заставил бы каждого потребителя заново разбираться с загрузкой и
ошибкой, хотя ответ давно известен, и добавил бы вопрос кеширования. Абстракция
заводится там, где окупается — на воспроизведении.

**`DeviceGate` решает только, какой случай наступил.** Все исходы — загрузка,
неподдерживаемое устройство, успех — приходят снаружи параметрами, загрузчик
тоже инжектируется. Виджет тестируется без платформенного канала. Попутно
закрыт случай ошибки: раньше исключение в `loadDeviceInfo()` вешало приложение
на чёрном экране навсегда.

**`PlayerScreen` + `PlayerView`.** Первый владеет блоком, второй рисует —
чтобы widget-тесты могли подставить свой блок вместо настоящего media_kit.

**Видимость оверлея — отдельный `OverlayVisibilityCubit`.** Это состояние
презентации, и в видеоконтроллере ему было не место: таймер скрытия жил дольше
виджета, который его завёл, а обратный вызов `onOverlayHided` держал ссылку на
уничтоженный `State`. Теперь таймер отменяется в `close()`, а «оверлей скрылся»
это просто переход состояния, на который подписывается `BlocListener` — обратной
ссылки из сервисного слоя в презентационный не осталось.

Начальное состояние воспроизведения — обязательный параметр конструктора.
Сначала я передавал его через `BlocListener`, и оверлей перестал скрываться
вовсе: слушатель срабатывает только на *изменение*, а кубит создаётся уже после
старта воспроизведения, когда менять нечего. Обязательный параметр делает эту
ошибку невозможной.

**Зависимости блока — только через конструктор.** Читать провайдер изнутри
блока нельзя (у него нет `BuildContext`), но и не нужно: иначе конструктор
перестаёт описывать, что блоку требуется, а тесты обрастают окружением.

## Компромиссы

**Ссылка указывает на одиночный HLS-вариант, а не на мастер-плейлист.** Это
уступка эмулятору (см. выше). Для продакшена нужен мастер: без него зритель со
слабым каналом получит буферинг вместо автоматически пониженного качества.

**Язык.** Код, комментарии и коммиты — на английском, документация — на русском,
по языку задания.
